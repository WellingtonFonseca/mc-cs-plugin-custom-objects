categoria: testes
regras:
- `Tests/Functional` (31 files) needs the Mautic monorepo and a dedicated test database and never runs in this stack; the live scripts of `scripts/5/` cover the same ground through the real HTTP API and commands.
- Plugin unit suite, in the web container: `docker exec --user www-data mautic-mautic_web-1 sh -c "cd /var/www/html/docroot/plugins/CustomObjectsBundle && php /var/www/html/vendor/bin/phpunit --do-not-cache-result -c Tests/Infection/phpunit.xml"`. The plugin's own `phpunit.xml` needs the monorepo. AbstractFieldControllerTest is excluded (abstract: PHPUnit warns and Infection stops on a warning).
- Alternative without config: `/var/www/html/vendor/bin/phpunit --no-configuration --bootstrap /var/www/html/vendor/autoload.php Tests/Unit` (the plugin's phpunit.xml points to an autoload.php that does not exist in the container). Two errors remain: CustomItemExportCommandTest and ExportControllerTest extend MauticMysqlTestCase (functional tests kept under Tests/Unit). A single test file may fail on the undefined MAUTIC_TABLE_PREFIX: run the suite or the whole Helper folder.
- The container runs PHPUnit 10.5: `Tests/Unit/ConsecutiveCallsTrait.php` replaces `withConsecutive()` (removed in 10) and `returnsThenNull()` keeps the old 'null after the last configured value' behavior. Do not reintroduce `withConsecutive()`.
- Coverage: `php -d pcov.enabled=1 /var/www/html/vendor/bin/phpunit --do-not-cache-result -c Tests/Infection/phpunit.xml --coverage-text` (PCOV, see [../../wiki/tests-mutation-and-coverage.md](../../wiki/tests-mutation-and-coverage.md)).
- Mutation testing: `infection --configuration=Tests/Infection/infection.json5 --threads=8 --no-progress --initial-tests-php-options='-d pcov.enabled=1' --min-msi=0 [--filter=File.php]`; about a minute for the whole plugin; report `/tmp/infection-co/infection.log`. Reads Model, EventListener, Helper, Segment, CustomFieldType, Provider, DTO and Repository. What is left escaped is noise (empty table prefix, casts, event priorities, JS/SQL fragments checked live) or needs a real database.
- `Tests/Infection/bootstrap.php` registers the project autoloader WITHOUT nikic/php-parser (Infection brings its own; loading both is a fatal error); without it Infection stops with 'Class ... does not exist' for classes extending Mautic's. Paths in infection.json5 and phpunit.xml are relative to the file; the bootstrap path of infection.json5 is relative to the plugin folder.
- The Infection folder is under `Tests/` on purpose: `Config/services.php` loads EVERY .php file under the plugin root into the container (excluding Tests/ and a few others), so a bootstrap elsewhere is executed by cache:clear and the plugin-boots test (memory exhausted by the classmap).
- A PHP warning in any unit test stops Infection (failOnWarning). Do not commit `Tests/Infection/.phpunit.result.cache` (cacheResult is off).
- `LeadRepository::exists` does not exist in Mautic 5.2, so CustomItemImportModelTest is skipped here and the unknown-contacts warning of an import is unreachable; CustomItemImportModelFlowTest covers the rest.
- Tests of query builders use the real ORM and DBAL builders (a mock accepts the wrong call), see `CustomItemModelTest`.
- Live scripts compute the expected ids from the value tables / their own data, not from the code under test; a test that sets the settings itself (CustomObjectMergedFilterQueryBuilderTest) proves nothing about the environment's config: use the live scripts for that.
- MCP tools (`Mcp/`) are proven by `scripts/5/test-mcp-custom-objects-sync.sh`: a real MCP client (JSON-RPC over HTTP, OAuth2 Bearer) from master 8080 to target 8081 (get_definition, apply dryRun/real/rerun, add-only, bad args, no permission, no token). Needs the 8081 stack up (`project/mautic-5-mcp`). Calling the PHP services or REST instead does not count as proof.
- Item tools (custom_objects_search/get/save/delete_items) are proven by `scripts/5/test-mcp-custom-items.sh` (same client and stack). Trap: save dryRun does not validate attribute values, and the real save does not reject an unknown select option or a non-numeric int (same as REST); only url and required fail. Do not assert those as errors.
- Live tests use own data per run under a RUN_ID and clean it on EXIT (never touch seeded objects); a field alias is unique in the WHOLE instance and must be clean (lower case, letters, digits, hyphen), so tests make '<runid><field>'.
- See the real SQL of a segment: as MySQL root `SET GLOBAL log_output='TABLE'; SET GLOBAL general_log=1;` run `mautic:segments:update --list-id=N`; read `mysql.general_log` for 'custom_item_xref_contact cix'; then `SET GLOBAL general_log=0; TRUNCATE mysql.general_log; SET GLOBAL log_output='FILE'`. Always turn the log back off.
- Default config without env vars: run the console with `env -u MAUTIC_CUSTOM_OBJECT_MERGE_FILTER -u MAUTIC_CUSTOM_OBJECT_ITEM_VALUE_TO_CONTACT_RELATION_LIMIT` (as www-data, after a cache:clear in the same state); the effective values must read true and 0 from the plugin default alone.
